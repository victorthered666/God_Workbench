# 内存安全排查与修复

日期：2026-11-13。**2026-11-13 更新：代码栈已迁移为 Rust 原生实现，本文所有限制已同步移植为 Rust 常量与集成测试（`src/config.rs`、`src/agent/vision.rs`、`src/tools/http.rs`），并通过 `cargo test` 覆盖。**

## 事故根因

测试日志 `Bash_348_181dfdd5-stdout.log` 明确记录：旧版 `split_title()` 在 `per_line = 0` 时循环无法推进，持续向列表添加空字符串，最终触发 `MemoryError`。这与测试期间出现的数十 GB 内存消耗一致。

这不是已确认的 Python GC 泄漏，而是无进展循环导致的无界内存分配。正常 A4 标题宽度不是事故的必要条件，异常窄宽度测试触发了该分支。

## 已修复

1. **标题换行硬性终止保证**
   - `app/export/cover.py`
   - 空标题、非正页面宽度、超长标题直接拒绝。
   - 行宽至少为 2，且每轮必须消耗字符；未推进立即抛错。
   - 标题最多 120 字，避免无意义的大输入。

2. **视觉图片有界编码**
   - `app/agents/vision.py`
   - 最多 6 张图；单图最长边 1920px、像素上限 1200 万。
   - 单张编码后最多 2 MiB，总编码数据最多 8 MiB。
   - 原图先转缩略 JPEG，不再直接 Base64 编码多张大图。
   - 图片 Base64 不写入会话数据库；编码后释放调用方副本。

3. **Agent 上下文与会话限制**
   - `app/agents/runtime.py`
   - 单次文本输入最多 2 MiB；工具结果最多 256 KiB；会话文本最多 6 MiB。
   - 调研历史最多引用 12 条、64 KiB 摘要。
   - 会话只保留受限文本，不保留图片和完整工具结果。
   - 任务结束清空本次消息列表。
   - 模型响应使用流式读取，最多 8 MiB。

4. **检索与网络生命周期**
   - `app/tools/__init__.py`
   - 搜索响应使用流式读取，最多 8 MiB。
   - HTTP 客户端每次请求创建并关闭，不再随工具注册表长期保留。
   - 抓取正文最多 32K 字符；检索正文进入模型前最多 16K 字符。
   - 测试通过 `httpx.MockTransport`，不再访问真实 API。

5. **图片处理与历史读取**
   - 超大图片标注前缩放，显式关闭 RGB 图像和画布。
   - 项目首页只读取项目摘要和最近审核结果。
   - 项目详情版本、证据按数量限制读取；归档仍保存全部历史。
   - 正文超过 2 MiB 时明确拒绝，后续应按章节拆分而不是继续拼接提示词。
   - `Runner` 完成任务后清理项目令牌引用。

## 验证

- `pytest`：23 项通过。
- `tools/memory_guard_test.py`：Windows Job Object 设置 **256 MiB** 进程地址空间上限，完成 1000 轮极限标题输入和 30 轮视觉图片负载处理，正常结束。
- 首页、项目详情、导出接口：HTTP 200。
- 修复后重启服务，实际 Python 进程工作集约 **75 MiB**（单时刻观察，不等于长期峰值保证）。
- 没有删除项目或修改用户的环境密钥。

## 后续边界

- 当前凭证无法完成真实 DeepSeek/豆包大图与长上下文线上验证，因此真实供应商返回的极端数据仍需有效凭证后验证。
- 目前限制可防止已识别的无界增长，但不能替代长时间线上监控。建议后续增加服务内存指标、每项目证据数量预算及分章文档任务。
- 不要通过提高内存上限来恢复旧版零宽换行行为；应先验证所有循环都有进展保证。

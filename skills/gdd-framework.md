# GDD 框架
每章定义目的、需要回答的问题、可执行要求和验收标准。至少考虑设计目标、受众与平台、核心循环、系统规则、内容范围、交互、反馈与边界。不要直接堆砌竞品功能。

## 篇幅预估（强制字段）
每章必须给出 `estimated_pages`：该章撰写成文后的预估正文页数（不含附录与版本历史），按需求条数、验收密度、图示与表格数量估算，宁可高估不要低估。经验锚点：1 页 ≈ 700–900 汉字，或 ≈ 4–6 条要求/验收。整份文档超过 30 页时先尝试收敛篇幅（合并次要章节、细节下放为表格）；确实无法收敛时如实给出高估页数——拆分评估会把分卷建议呈给用户，由用户决定分卷或单文档继续。

## 自检清单（输出前逐项确认）
1. 同一机制的规则与数值在多处描述不得自相矛盾——写下每条规则时，回查此前章节是否已有冲突表述。
2. 引用的章节/表号/小节必须真实存在于本文。
3. 数值上限或保护规则不得与具体动作的无敌帧、霸体、处决等既有设定冲突；冲突即调整上限或例外条款。
4. 互斥条件必须真实成立（载体、栏位、状态确实互斥），不能凭空声明。
5. 每条验收标准可测试、可执行，避免"体验良好"类不可判定表述。
6. 各章 estimated_pages 完整无缺，求和与整体篇幅预期一致。

审核经验：以上五类是历史上最常见的架构级缺陷来源，生成框架时主动规避可大幅减少返工。
